# Hajime Pro (hajime-pro)

Turnierverwaltungssoftware für Judo-Wettkämpfe nach den Regeln des Deutschen Judo-Bundes (DJB) — deckt den gesamten Ablauf von der Anmeldung bis zur Siegerliste ab. Kein Scoring/Refereeing-Tool (keine Ippon/Waza-ari/Shido-Erfassung), sondern reine Wettkampf-Organisation: Teilnehmerverwaltung, Auslosung, Matten-/Zeitplanung, Live-Steuerung, Ergebnisanzeige.

## Tech-Stack
- **Backend:** Node.js (ES-Module) + Express, Knex als Query-Builder/Migrations
- **DB:** PostgreSQL (Cloud: Supabase oder eigener Server; Hallen-Server: lokal). SQLite wurde entfernt (`DB_CLIENT=sqlite` verhindert den Start; ein bestehendes Turnier lässt sich per Turnier-Export/-Import übernehmen). Welche Datenbank und welche Rolle gilt, entscheidet `BETRIEBSMODUS` (siehe Commands)
- **Frontend:** Server-gerenderte statische HTML-Seiten in `public/` + Vanilla-JS, Material Components Web für UI, `jsqr`/`qrcode-generator` für QR-Scanning (Judopass) an der Waage
- **Auth:** JWT (`jsonwebtoken`), vereinsbasierte Zugriffsrechte

## Commands
- **Betriebsmodi (`BETRIEBSMODUS`, ausgewertet einmal in `src/config/betriebsmodus.cjs`):** `cloud` (Internet-Server, PostgreSQL/Supabase, Vereinsrechte mit Login), `server` (Hallen-Server: PostgreSQL + Dokument-DB lokal, Einzelbenutzer ohne Login; auf einem Notebook unter Windows/macOS/Linux oder auf Linux-Servern, dort optional im Cluster) und `client` (Gerät an Matte/Waage, nur lokale Dokument-DB, Installation über den Server). Ein Server bietet seine Dienste immer gleich an (alle Schnittstellen, mDNS `turnier.local`, Port 80): ob der Browser auf demselben Rechner läuft oder ein Client im LAN zugreift, macht keinen Unterschied, und ohne Netzwerk läuft er ebenfalls (nur `LISTEN_HOST=127.0.0.1` beschränkt ihn auf localhost). Ergänzend im Modus `server`: `CLUSTER_KNOTEN` (Cluster braucht einen eigenen PostgreSQL-Server) und `DB_HOST`/`DB_URL`: **ohne `DB_HOST`/`DB_URL` startet der Server sein eigenes, eingebettetes PostgreSQL** (`src/utils/eingebettetesPostgres.js`, Binaries aus `embedded-postgres`, Datenverzeichnis `PG_DATENVERZEICHNIS`, Standard `./data/pg`, Port `DB_PORT`, Standard 5433, nur `127.0.0.1`, Log neben dem Datenverzeichnis; Schema wird bei jedem Start migriert; läuft bereits eine Instanz, wird sie übernommen; nicht als root startbar), mit `DB_HOST` nutzt er einen vorhandenen Server. Das eingebettete PostgreSQL gilt nur bei ausdrücklich gesetztem `BETRIEBSMODUS=server`; Rauchtest: `node scripts/smoke-server-eingebettet.mjs` (CI-Job `server-selbststart` auf Ubuntu/Windows, macOS vorerst nicht in der CI). Ungültige Kombinationen verhindern den Start mit Meldung. **Ohne `BETRIEBSMODUS`** gilt das bisherige Verhalten aus den Altvariablen: `SYNC_ROLLE=client` → `client`, `IS_OFFLINE=true` → `server` (PostgreSQL über `DB_HOST`/`DB_URL`, ohne diese Angabe Startabbruch mit Hinweis auf `BETRIEBSMODUS=server`; kein eingebettetes PostgreSQL; die Sync-Rolle kommt dort allein aus `SYNC_ROLLE`, also auch ein Server ohne Sync möglich — so laufen `test:e2e` und der Offline-Teil von `test:e2e:vollablauf`), sonst `cloud`. Im Code fragt man `betriebsmodus.liesBetriebsmodus()` bzw. `istEinzelbenutzerBetrieb()`, nie direkt `process.env.IS_OFFLINE`
- **Dev-Server starten:** `npm start` (= `node src/app.js`), liest `.env` (`BETRIEBSMODUS`, `PORT`, DB-Zugangsdaten); Standardport 3000
- **DB-Umschaltung:** PostgreSQL über `DB_HOST`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`/`DB_PORT` (knex-Umgebung `online`, daneben `online-migration`); es gibt nur noch PostgreSQL (`src/utils/dbUmgebung.js` → `betriebsmodus.cjs`)
- **Sync-Modus (Hallen-Server):** `BETRIEBSMODUS=server` (bzw. altes `SYNC_ROLLE=server`) (+ optional `SYNC_DATENVERZEICHNIS`, Standard `./data/dokumente`, und `SYNC_SECRET`) aktiviert die eingebettete Dokument-DB unter `/db`; genau ein Turnier pro Server, Anlegen/Import eines Turniers löscht das bisherige
- **Client-Gerät (Notebook/Tablet an Matte/Waage):** `BETRIEBSMODUS=client` (bzw. altes `SYNC_ROLLE=client`), `SYNC_SERVER_URL=http://<hallen-server>:3000`, `SYNC_SECRET` (wie am Server), optional `SYNC_DATENVERZEICHNIS`; `npm start`, Browser auf `http://localhost:3000` (Startseite `client.html`). Keine relationale DB, keine `DB_*`-Variablen nötig. Unter Windows das Datenverzeichnis möglichst vom Virenscanner ausnehmen (LevelDB-Dateien werden sonst gelegentlich beim Anlegen blockiert; `oeffneMitWiederholung` fängt das ab)
- **Server-Cluster, Hallen-Server-/Cluster-Installation, Cloud/Docker, CI/Release, Server-Paket, Desktop-Client, Android-App, Client-Dateien:** Geräte-/Rollen-Matrix in [`docs/betriebsarten.md`](docs/betriebsarten.md), Betriebs- und Release-Details in [`docs/betrieb.md`](docs/betrieb.md); Cluster-Betrieb zusätzlich in `deploy/linux/README.md`, Desktop in `desktop/README.md`. Wichtig: `npm run ci:lokal` lässt die CI vorab lokal laufen (der Pre-Push-Hook nutzt die schlanke Variante `--schlank`: Unit-Tests + nur die zu den noch nicht gepushten Änderungen passenden E2E-Specs, volle Suite mit `npm run ci:lokal` bzw. in der CI; Umgehen nur mit `HAJIME_CI_UEBERSPRINGEN=1`); `test:e2e:vollablauf` läuft bewusst nicht in der CI.
- **Migrationen:** kein npm-Script dafür — direkt über knex ausführen, z.B. `npx knex migrate:latest --knexfile knexfile.cjs --env online` (ohne `--knexfile` findet knex die `.cjs`-Datei nicht); Konfiguration in `knexfile.cjs`, Dateien in `migrations/`

Für den lokalen Server-Modus: `IS_OFFLINE=true`, `DB_HOST=127.0.0.1`, `DB_PORT=5433`, `SYNC_ROLLE=server`

## Domänenmodell (Kernentitäten)
- **`vereine`** — Judo-Vereine; jeder Nutzer (`benutzer`) gehört zu genau einem Verein (`verein_freigegeben`-Flag für Mitgliedschafts-Freigabe)
- **`turniere`** — ein Wettkampftag, gehört einem ausrichtenden Verein, hat Status-Lifecycle (`geplant` → `abgesagt`/`abgeschlossen`)
- **`kampfflaechen`** — die Matten eines Turniers
- **`pools`** — die eigentlichen Wettkampfklassen (Alters-/Gewichtsklasse + Geschlecht), jeweils mit Modus (Jeder-gegen-Jeden, Doppel-KO-8/16/32, Gruppen-Überkreuz), Kampfzeit und Golden-Score-Einstellungen
- **`turnier_teilnehmer`** — angemeldete Athlet:innen (Judopass-ID, Gewicht, Verein, zugeordneter Pool)
- **`kaempfe`** — einzelne Kämpfe innerhalb eines Pools, verknüpft per `..._quelle_kampf_id/_typ` mit ihren Vorgängerkämpfen (Bracket-Verkettung); bei Mannschaftskämpfen zusätzlich per `mannschaftskampf_id`/`mannschaft_gewichtsklasse` einer Begegnung zugeordnet
- **`mannschaften`** — eine Mannschaft in einem Mannschafts-Pool (`pools.typ = 'mannschaft'`), Verein als freier Text (analog `turnier_teilnehmer.verein`)
- **`mannschaft_mitglieder`** — ordnet vorhandene `turnier_teilnehmer` einer Gewichtsklassen-Position der Mannschaft zu (der Judoka bleibt ein normaler `turnier_teilnehmer`, Wiegen/QR-Scan laufen unverändert über `waage`)
- **`urkunden_vorlagen`** — Urkunden-Vorlagen je Verein (Blanko-PDF, Textfelder, waagerechte Linien (`typ: 'linie'`) und Bilder (`typ: 'bild'`, PNG/JPEG in der Spalte `bilder`) als JSON in pt mit Ursprung oben links; die Spalten `platzbereich`/`reihenfolge`/`bei_abschluss_anbieten` werden nicht mehr genutzt); wandern mit dem Turnier-Export zum Hallen-Server, aber nicht zurück
- **`urkunden_pdfs`** — das zuletzt erzeugte Urkunden-PDF je Pool (höchstens eines, samt Vorlage/Platzbereich/Reihenfolge/Anzahl/`erzeugt_am`); `/urkunden/generieren` legt es ab (am Secondary nicht), `urkunden.html` zeigt es je Pool an und bietet Öffnen/Neu erzeugen/Löschen (`/api/urkunden/pools/:poolId/pdf`); nicht Teil des Turnier-Exports
- **`mannschaftskaempfe`** — eine Begegnung (Team A vs. Team B) innerhalb eines Mannschafts-Pools, strukturell parallel zu `kaempfe` (gleiche Status-Werte, gleiches Quelle-Verknüpfungsmuster für die Bracket-Kaskade); ihre Einzelkämpfe (einer pro gemeinsam besetzter Gewichtsklasse) sind ganz normale `kaempfe`-Zeilen

## Zentrale Architekturkonzepte
- **Routen als Factories mit Knex-Dependency-Injection:** jede Datei in `src/routes/` exportiert eine Funktion (`getXRoutes(knex)`), die in `src/app.js` mit der einen zentral erzeugten Knex-Instanz (Online/Offline je nach `IS_OFFLINE`) aufgerufen und gemountet wird; alle Schreib-Routen (`/api/turniere`, `/api/teilnehmer`, `/api/pools`, `/api/kampfflaechen`, `/api/kaempfe`, `/api/mannschaften`, `/api/mannschaftskaempfe`) laufen zusätzlich durch `requireWriteAuth` (`src/middleware/auth.js`); `/api/auth` und `/api/vereine` bewusst ohne dieses Gate (Login/Registrierung/Vereinsauswahl)
- **`src/shared/`** ist bewusst framework-/DB-frei gehalten (kein knex, kein DOM) und läuft identisch am Server und auf Client-Geräten (Offline-Kaskade, Mattenansicht):
  - `bracketTopologie.js` — deklarative Turnierbaum-Struktur pro Modus (welcher Kampf bezieht seine Kämpfer aus welchem Vorkampf)
  - `kampfProgression.js` — Kaskaden-Engine: befüllt Folgekämpfe erst, wenn beide Kämpfer-Slots feststehen
  - `pausenRegel.js` — Mindestpausenzeiten zwischen Kämpfen eines Athleten (DJB-WKO)
  - `mannschaftsProgression.js` — Kaskaden-Engine für Mannschaftsbegegnungen, das Pendant zu `kampfProgression.js` auf Ebene der Begegnungen statt der Einzelkämpfe
  - `platzierungen.js` — Platzierungen je Pool inkl. Platz 5/7 (Einzel und Mannschaft), gemeinsam für Siegerliste und Urkunden
  - `urkundenText.js` / `urkundenSchriften.js` — Platzhalter, automatische Verkleinerung, Basislinie und die mitgelieferten Schriften (`public/fonts/urkunden/`), identisch im Editor und beim PDF-Rendern
- **Teilnehmer-Import aus E-Mail (Drag & Drop auf `teilnehmer.html`, ohne KI):** `src/shared/mailExtraktion.js` (browser-/node-identisch, Tests `tests/unit/mailExtraktion.test.js`) liest `.eml` (MIME, Quoted-Printable/Base64, HTML→Text, Anhänge), Outlook-`.msg` (`src/shared/msgParser.js`, eigener CFB-Leser, Klartext-/HTML-Körper und Anhänge, kein reiner RTF-Körper) oder gezogenen Text und findet Kämpfer regelbasiert (Freitext-Zeilen mit Geburtsdatum/-jahr, Geschlecht, Gewicht, Kyu/Dan, Pass-Nr., Verein-/Geschlechts-Kontextzeilen sowie Tabellen mit Kopfzeile); ohne erkennbaren Text wird ein XLSX/CSV-Anhang genommen, `.msg` wird abgelehnt. Das Ergebnis läuft als CSV durch die normale Import-Vorschau (`previewTeilnehmerImport` mit `alleZeilen`), in der die Zellen bearbeitbar sind und Zeilen entfernt werden können (`mailTabelle` in `teilnehmer.js`); gespeichert wird erst mit "Import starten". E2E: `tests/e2e/teilnehmer-import-email.spec.js`
- **Urkunden (`/api/urkunden`, `urkundenController.js`, `services/urkundenRenderer.js` mit pdf-lib + fontkit, `services/urkundenDaten.js`):** Designer auf `urkunden-designer.html` (Fabric.js + pdf.js, Linien-Muster aus `src/shared/urkundenLinien.js`, Bilder über `services/urkundenBilder.js`; neue Vorlagen wahlweise aus einem der fünf Standard-Rahmen in `public/urkunden-rahmen/` — Liste `src/shared/urkundenRahmen.js`, erzeugt von `scripts/erzeuge-urkunden-rahmen.mjs`), Generieren auf `urkunden.html`, ein PDF mit einer Seite je Urkunde; Vorlagen-Auswahl mit Mini-Ansicht (`/vorlagen/:id/vorschau`) und das Druck-Angebot nach „Pool abschließen“ (immer, sobald der Verein mindestens eine Vorlage hat; Vorlage/Platzierungen/Reihenfolge wählbar) in `public/js/urkundenDruck.js`. Reihenfolge `absteigend` (letzter Platz zuerst, früher `siegerehrung`) oder `aufsteigend`. `/urkunden/generieren` ist in `nurMaster` ausgenommen (Druck auch am Secondary). Vorlagen-Austausch zwischen Vereinen/Installationen: Designer-Knöpfe „Exportieren“/„Importieren“ (`GET /api/urkunden/vorlagen/export?ids=`, `POST /vorlagen/import`), Dateiformat `.hajime-urkunde.json` (Format-Kennung `hajime-urkunden-vorlagen`, Version, PDF und Bilder als Base64, ohne Voreinstellungen) in `services/urkundenVorlagenDatei.js`; Import überschreibt nie (Namenskonflikt → „Name (2)“) und meldet ungültige Vorlagen mit Grund. Spec: `docs/specs/2026-09-29-urkunden-generator-design.md`
- **Waage in Runden (Spec `docs/specs/2026-10-08-waage-runden-design.md`):** Pools werden je Altersklasse ausgelost, nicht mehr für das ganze Turnier auf einmal. `POST /api/pools/generieren` nimmt `altersklassen: string[]` (ohne Angabe: alle, wie früher); `GET /api/pools/altersklassen-status` liefert je Altersklasse `kampfbereit/angemeldet/gesamt/ausgelost/hatEchteKaempfe`. Der Zustand einer Altersklasse wird nur aus den Einzel-Pools abgeleitet (`ermittleAltersklassenPoolZustand` in `poolController.js`, keine neue Spalte): *ausgelost* = es gibt einen Pool, *gesperrt* = ein Pool davon hat echte Kämpfe. Die Teilnehmer-Sperre (`teilnehmerController.js`) gilt je Altersklasse (Anmelden in ausgeloste Klasse → 409; Ändern/Löschen bei gesperrter Klasse → 409); `GET /api/pools/vorhanden` liefert `gesperrteAltersklassen`/`ausgelosteAltersklassen` (und `gesperrt` als Alias), `src/shared/clientAntworten.js` rechnet dasselbe für Client-Geräte. Mannschaften und Mannschaftsmitglieder sind erst gesperrt, wenn ein Mannschafts-Pool echte Kämpfe hatte (`mannschaftsPoolsHabenEchteKaempfe`); Einzelkämpfe sperren sie nicht. Matten-Verteilung: reine Funktion `src/services/mattenVerteilung.js` (`verteilePoolsAufMatten`); `POST /api/pools/aufteilen` hat `modus: 'neue'` (Standard, hängt nur Pools ohne Matte an die bestehende Belegung an) oder `'alle'` (Knopf „Alle neu verteilen“ auf `matten.html`)
- **`src/services/*Manager.js`** — Turniermodus-Implementierungen (DoppelKo8/16/32Manager, GruppenUeberKreuzManager, JederGegenJedenManager), erzeugen die Kämpfe eines Pools beim Anlegen; für Mannschafts-Pools die entsprechenden `Mannschaft*Manager.js` (Jeder-gegen-Jeden, Doppel-KO-8/16), die Begegnungen statt Einzelkämpfe erzeugen
- **`src/services/mannschaftsBegegnungEngine.js`** — erzeugt pro Begegnung die Einzelkämpfe je gemeinsam besetzter Gewichtsklasse, wertet Sieg-/Wertungspunkte aus und lost bei vollständigem Gleichstand automatisch einen Stichkampf aus (DJB-WKO Art. 3.12.13.1); das Abschenken-Verbot (Art. 3.12.13.3) hängt in `teilnehmerController.js` an den bestehenden „nicht angetreten“/„disqualifizieren“-Aktionen
- **Offline-Betrieb an der Matte/Waage:** Client-Geräte (`SYNC_ROLLE=client`, siehe unten) laufen mit lokaler PouchDB weiter, wenn das WLAN zum Hallen-Server wegbricht, und replizieren automatisch nach. Der frühere JSON-Export/-Import pro Matte (`/api/offline`, Browser-Offline-Modus in `steuerung.html`) ist entfallen; Datei-Austausch gibt es nur noch für ganze Turniere (Cloud ↔ Hallen-Server, Turnier-Export/-Import mit `urspruengliche_id`)
- **Sync-Schicht (CouchDB-Umbau, `src/sync/`):** mit `SYNC_ROLLE=server` betreibt der Hallen-Server eine eingebettete Dokument-DB (PouchDB/LevelDB, `express-pouchdb` unter `/db`, eine DB `turnier_<instanz_id>` für das einzige Turnier; das vorhandene Turnier wird verzögert beim ersten `/api`-/`/db`-Request aktiviert). `abgleich.js` spiegelt die Live-Tabellen nach jedem Schreibzugriff als Dokumente (`bearbeitet_von: 'server'`, Typ in `dokumenttyp`), `bruecke.js` wendet Dokument-Änderungen von Waage/Scoreboard/Mattenleitung über die Service-Funktionen der Controller an (`aktualisiereKampf`, `werteForfeit`, `legeTeilnehmerAn`, …; werfen `FachFehler`) und meldet Ablehnungen per `letzte_ablehnung` + `konflikt:`-Dokument zurück. Das Frontend spricht über `public/js/datenzugriff.js` (REST ohne Sync, Dokument-DB mit Sync). Die relationale DB bleibt führend. Die Brücke ist reihenfolgeunabhängig (Replikation liefert nicht in Spielreihenfolge): Ergebnisse mit abweichender Paarung werden zurückgestellt und nachgeholt, bleibt die Abweichung, wird der Kampf `klaerung` (Konflikt hoch); CouchDB-Konflikte löst sie so, dass Geräte-Revisionen vor Server-Revisionen gewinnen, bei Wiegungen die jüngste (`gewogen_am`). Konfliktliste: eigene Seite `sync-konflikte.html` (`public/js/konflikte.js`, `/api/sync/konflikte`, Gegenüberstellung Gerät/Server mit Kämpfernamen; Klärungsfälle entscheidet die Turnierleitung dort per `POST /api/sync/konflikte/:id/entscheiden` (`entscheidung: 'geraet'` übernimmt Paarung+Ergebnis des Geräts, `'server'` stellt den Kampf auf seinen Status vor der Klärung zurück; `entscheideKlaerung` in `bruecke.js`); Menüpunkt „Sync-Konflikte“ mit Zähler offener Konflikte, nur am Hallen-Server). Design: `docs/specs/2026-09-25-couchdb-umbau-design.md`

## Mannschaftskämpfe
Mannschafts-Pools (`pools.typ = 'mannschaft'`) laufen als Team-vs-Team-Begegnungen: pro fest
definierter Gewichtsklassen-Position (`pools.mannschafts_gewichtsklassen`, DJB-Vorlage für U15/U18
m/w, sonst aus den Einzelwettkampf-Gewichtsklassen übernommen oder frei editierbar) ein
Einzelkampf; Sieger der Begegnung = mehr Kampfsiege, bei Gleichstand Wertungspunkte, bei
vollständigem Gleichstand automatischer Stichkampf. Unterstützte Turniersysteme: Jeder-gegen-Jeden
und Doppel-KO-8/16 (Doppel-KO-32 und Gruppen-Überkreuz für Mannschaften bewusst noch nicht
umgesetzt). Mannschafts-Pools werden manuell angelegt (kein automatisches Bulk-Auslosen aus
Einzelanmeldungen) und komplett auf der eigenen Seite `mannschaften.html` verwaltet — sie
erscheinen bewusst nicht in `pools.html`/`pools.js`, deren Rendering strukturell auf
Einzelwettkampf-Pools zugeschnitten ist. Bundesliga-Ligabetrieb (Startgenehmigungen,
Transferfenster, Kampfgemeinschaften, Fremdstarter-Kontingente) ist explizit außerhalb des Scopes
— das ist überjährige Vereinsverwaltung, kein Turniertag.

## Umfang / bewusste Auslassungen
- Kein separater Team-Ligabetrieb (Bundesliga-Startgenehmigungen/Transferfenster) — siehe
  „Mannschaftskämpfe“ oben; einzelne Turniertage mit Mannschaftskämpfen sind abgedeckt
- Keine Kampfrichter-/Scoring-Logik (IJF-Kampfregeln zu Wurftechniken/Bewertungen sind nicht Teil der Anwendung)

## Seitenstruktur (`public/`)
`login` → `verein_auswahl` → `turniere` (Turnierauswahl) → `turnier`/`teilnehmer`/`pools`/`mannschaften` (Verwaltung) → `matten`/`steuerung`/`kampf` (Live-Betrieb am Wettkampftag) → `waage` (Einwiegen per QR-Scan) → `anzeige`/`dashboard`/`siegerliste` (öffentliche Anzeigen) → `urkunden` (Urkunden-Druck), `urkunden-designer` (Vorlagen-Editor); `cluster` (Status des Server-Clusters, nur Hallen-Server mit `CLUSTER_KNOTEN`), `client` (Startseite eines Client-Geräts), `download` (öffentlich, Download der Desktop-Client-Installationsdateien und der Android-App); nur in der Android-App: `verbinden` (`mobil/web/`, Kopplung)
