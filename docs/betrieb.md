# Betrieb, Installation und Release

Übersicht, welche Geräte Server oder Client sind: [`betriebsarten.md`](betriebsarten.md). Aus `CLAUDE.md` ausgelagert (Stand v1.0.10). Hinweise zu Betriebsmodi, DB und Tests stehen weiter in `CLAUDE.md`.

- **Server-Cluster (zwei Hallen-Server, Master/Secondary):** zusätzlich zu `BETRIEBSMODUS=server` (PostgreSQL ist dort Standard): `SYNC_SECRET` (Pflicht im Cluster, auf beiden Servern gleich — ohne verweigert der Server den Start, `clusterSecretFehler` in `src/cluster/konfig.js`), `CLUSTER_KNOTEN` (`server1`|`server2`), `CLUSTER_PARTNER_URL` (feste Adresse des anderen Servers), optional `CLUSTER_VIP` (Anzeige), `CLUSTER_ZEUGE` (IP → Ping, URL → GET; leer = Default-Gateway), `CLUSTER_RUECKSTUFEN_BEFEHL` (Standard `sudo -n /usr/local/bin/hajime-rueckstufen.sh`). Ohne `CLUSTER_KNOTEN` ist der Server wie bisher immer Master. Betrieb (PostgreSQL-Replikation, keepalived, Skripte, Abnahme-Checkliste): `deploy/linux/README.md`
- **Neuen Hallen-Server aufsetzen (ein Befehl):** `sudo bash deploy/linux/install.sh` auf frischem Debian/Ubuntu (Node.js, PostgreSQL, `.env` mit Zufallsgeheimnissen, Migrationen, systemd-Autostart, ufw); wiederholbar als Update, kein Cluster (siehe `deploy/linux/README.md`)
- **Zwei-Server-Cluster einrichten (geführt):** `sudo bash deploy/linux/install-cluster.sh --knoten server1|server2 --eigene-ip … --partner-ip … --vip …` auf beiden Servern (server1 zuerst, Geheimnis-Datei per scp zu server2); installiert Node.js, PostgreSQL-Replikation, keepalived, `.env`, systemd, ufw; `hajime-cluster-status` zeigt den Zustand; `--nur-konfig <Verzeichnis>` erzeugt nur die Konfigurationsdateien (Unit-Test `tests/unit/install-cluster.test.js`, CI-Job `cluster-installation` baut den Cluster in zwei Docker-systemd-Containern auf und prüft Failover)
- **Cloud-Modus (`BETRIEBSMODUS=cloud`) und Docker:** PostgreSQL-Verbindung über `DB_URL` (Alias `DATABASE_URL`, z.B. Supabase-Pooler) oder die Einzelvariablen `DB_HOST`/…; die URL gewinnt (`src/config/dbVerbindung.cjs`, Unit-Tests `tests/unit/dbVerbindung.test.js`). `DB_SSL=true|no-verify|false` (Standard bei URL `no-verify`, sonst `false`; `sslmode` in der URL wird entfernt), `DB_POOL_MAX`, optional `DB_URL_MIGRATION` (Direct-/Session-Verbindung, Umgebung `online-migration` in `knexfile.cjs`, da der Transaction-Pooler keine Migrationen verträgt) und `DB_AUTO_MIGRATE=true` (migriert beim Start über `DB_URL_MIGRATION`, Standard aus). `Dockerfile` + `docker-compose.yml` (Profile `cloud` gegen Supabase, `lokal` mit eigenem Postgres), Konfiguration aus `.env.cloud.example` → `.env.cloud`; Healthcheck auf `/api/config`; Workflow `.github/workflows/docker-cloud.yml` baut das Image nur manuell (`workflow_dispatch`), nicht Teil von `ci.yml`
- **`PUBLIC_BASE_URL` (Links in Mails):** öffentliche Adresse für die Links in Registrierungs- (`/bestaetigen.html`) und Freischaltungs-Mails (`/freigabe.html`), nur http/https, wird auf den Origin gekürzt (`src/utils/basisUrl.js`). Im Modus `cloud` Pflicht: fehlt sie oder ist ungültig, antwortet `POST /api/auth/register` mit 503 und „Bestätigungsmail erneut senden“ verschickt nichts (Hinweis im Log); der Host-Header eines Requests wird dort nie für Mail-Links verwendet (Schutz vor Host-Header-Injection). Außerhalb der Cloud fällt sie auf Protokoll + Host des Requests zurück
- **Helferverwaltung (Cloud, Spec `docs/specs/2026-10-17-helferverwaltung-design.md`):** Registrierung und Freischaltung laufen über Mails (Bestätigungslink an die neue Adresse, Freischaltungslink an die Vereins-Admins): ohne funktionierenden SMTP-Versand (`SMTP_*`-Variablen, wie für die übrigen Mails) kommt niemand ins System; `PUBLIC_BASE_URL` ist in der Cloud Pflicht (siehe oben). Das Super-Admin-Konto `admin@example.org` bleibt bei jedem Start Super-Admin (`src/utils/superAdmin.js`); Nutzer und Rollen verwaltet er auf `admin-nutzer.html`. Die Helfer-App (`/api/helfer`, `helfer.html`) ist nur in der Cloud aktiv, `HELFER_APP_AKTIV=true` schaltet sie außerhalb der Cloud ein (Tests); der Helferplan der Orga (`/api/helfer-plan`, `helfer-plan.html`) läuft überall. Neue Migrationen `20261018100000` (Rollen, E-Mail-Bestätigung, `token_einmal`; Bestandsmitglieder mit Freigabe werden Admin, alle Konten gelten als bestätigt), `20261018110000` (Turnierzeiten, Helferplan-Tabellen) und `20261018120000` (`token_einmal.angefragt_ueber`). Automatisch laufen sie nur mit dem eingebetteten PostgreSQL (bei jedem Start), in der Cloud mit `DB_AUTO_MIGRATE=true` sowie über `install.sh`/`install-cluster.sh`/`update.sh` und das Selbst-Update des Linux-Dienstes; sonst vor dem Umschalten des Codes von Hand: `npx knex migrate:latest --knexfile knexfile.cjs --env online` (Cloud mit Supabase über `DB_URL_MIGRATION`, Umgebung `online-migration`). **Reihenfolge: Migration IMMER vor dem Code-Umschalten** — neuer Code auf altem Schema lässt jeden Login mit 403 scheitern und `GET /api/turniere` mit 500. Im Cluster zuerst den Master aktualisieren bzw. die Migration sofort nach dem ersten aktualisierten Knoten am Master ausführen (der Secondary ist nur lesend). **Cloud-Umstellung:** (1) Datenbank sichern; (2) Vorab-Check auf E-Mail-Dubletten (die Anmeldung sucht ohne Beachtung der Schreibweise): `SELECT lower(trim(email)), count(*) FROM benutzer GROUP BY 1 HAVING count(*) > 1;` – Treffer vorher zusammenführen bzw. umbenennen; (3) Migration, dann Code umschalten; (4) wurde der Code vor der Migration umgeschaltet oder sind in der Zwischenzeit Konten/Freigaben entstanden, nachträglich reparieren: `UPDATE benutzer_vereine SET rolle = 'admin' WHERE freigegeben = 1 AND rolle IS NULL;` und `UPDATE benutzer SET email_bestaetigt_am = now() WHERE email_bestaetigt_am IS NULL AND created_at < '<Zeitpunkt des Umschaltens>';`. **Ratenbegrenzung** (`src/middleware/authRatenbegrenzung.js`, nur Cloud bzw. `AUTH_RATENLIMIT_AKTIV=true|false`, im Speicher je Instanz, bei voller Tabelle wird verdrängt statt gesperrt): je Absender (IPv4 bzw. IPv6-/64, über `clientIp`, hinter eigenem Proxy `LIVE_PROXY_VERTRAUEN=true`) 10 Registrierungen, 10 „Bestätigungsmail erneut“ und 30 Logins je 10 Minuten; je E-Mail-Adresse 3 „Bestätigungsmail erneut“; Login zusätzlich 10 je Adresse+Absender und weich 60 je Adresse (alle Versuche zählen, auch erfolgreiche); Schlüssel aus dem Body nur als SHA-256, Antwort 429 „Zu viele Anfragen. Bitte versuche es später erneut.“, gleich für bekannte und unbekannte Adressen. Eine Bestätigungsmail geht höchstens alle 2 Minuten an dasselbe Konto (die Antwort bleibt gleich). `/api/auth` nimmt JSON-Bodys bis 10 kB (sonst 413), E-Mail-Adressen über 254 Zeichen werden mit 400 abgelehnt. Ohne SMTP loggt die Cloud nur Empfänger und Betreff einer Mail (keine Einmal-Links), außerhalb der Cloud den vollen Text. Eine im Profil geänderte E-Mail-Adresse wird (noch) nicht erneut bestätigt. Der Helferplan reist mit dem Turnier-Export zum Hallen-Server (Einsätze nur als Namen, keine E-Mails) und lässt sich dort über „Turniere aus der Cloud“ (`POST /api/cloud/turniere/:id/helferplan`) aktualisieren.
- **CI/Release-Pipeline (Stages dev → test → qa → prod):** `.github/workflows/ci.yml` (nur PR und manuell, auch als `workflow_call`; kein Push-Trigger auf `main` und kein Nachtlauf — der PR hat die Änderung bereits geprüft) — `dev` (Ubuntu, billig: `plan` mit Pfadfiltern via `dorny/paths-filter` aus `.github/ci-filter.yml` (dieselbe Datei liest `scripts/ci-lokal.mjs`; Abhängigkeiten zählen über `package-lock.json`, `package.json` allein löst nur den E2E-Kern aus), `unit`, `shellcheck`), `test` (`test:e2e` in 3 Shards (`--shard=n/3`, je eigener Runner mit eigenem Server und eigener DB; die Spec-Dateien hängen nicht voneinander ab) bei Änderungen an `src/`, `public/`, `migrations/`, `tests/e2e/` …; `test:e2e:sync` als eigener Job nur im PR und nur bei Änderungen an `src/sync`, `src/shared`, `datenzugriff.js`, `tests/e2e-sync`, `migrations`; das Release führt sie nicht erneut aus), `qa` (parallel zu `test`, startet nach grünem `dev`: `server-selbststart` auf Ubuntu/Windows nur bei Änderungen am eingebetteten PostgreSQL/Betriebsmodus/Migrationen, `cluster-installation` (Docker) + `e2e-cluster` nur bei `src/cluster|sync|shared`, `deploy/linux`, Cluster-Tests, `server-paket` (Aufruf von `server-paket.yml`, nur bei Paket-Pfaden, nicht bei Tag/Nachtlauf, kein eigener PR-Trigger mehr)); `test` und `qa` brauchen ein grünes `dev` (`needs`) und laufen parallel, `concurrency` bricht veraltete PR-Läufe ab. Voller Umfang ohne Filter bei Tag und manuellem Start (`plan` setzt dann alle Flags). **Release-PR (ändert nur das Feld `version` in `package.json`/`package-lock.json`):** `plan` erkennt den Versionssprung und lässt alle Test-Gruppen laufen, aber kein Server-Paket und keine APK (baut das Release). **Abschlussjob `CI-Ergebnis`** (Pflicht-Check für `main`, rot bei fehlgeschlagenem oder abgebrochenem Job, übersprungene zählen als bestanden); lief der volle Testumfang grün, legt er das Artefakt `ci-gruen-<Tree-Hash>` ab (30 Tage). `release.yml` prüft zuerst Tag/Version (`pruefen`, bei Fehler endet der Lauf nach Sekunden, ohne Tests) und sucht dann im Job `vorgeprueft` diese Marke für den Tree des Release-Commits (nur aus Läufen dieses Repos, nicht aus Forks) und überspringt dann `tests`; ohne Marke (z.B. wurde nach dem Release-PR noch ein anderer PR gemergt, dann weicht der Tree ab) laufen die Tests wie bisher. Den Release-PR deshalb vor dem Merge auf den Stand von `main` bringen („Update branch“). `test:e2e:vollablauf` läuft bewusst nicht mit (schreibt in die echte Cloud-DB). `.github/workflows/release.yml` (Tag `v*` oder manuell: Actions → Release → Run workflow, Branch `main`, Version ohne `v`; beim manuellen Start legt `gh release create --target <Commit>` den Tag selbst an, bricht ab, wenn der Tag schon existiert oder der Branch nicht `main` ist; `RELEASE_TAG` ersetzt `GITHUB_REF_NAME`; `ci.yml` bekommt `release: true`, damit Server-Paket und APK nicht doppelt gebaut werden; Stage `prod`) ruft `ci.yml` auf, prüft Tag == `package.json`-Version, baut den Desktop-Client für Windows/macOS/Linux (+ Electron-Rauchtest je Plattform) und parallel das Server-Paket (`server-paket.yml`), signiert die Client-Dateien und veröffentlicht beides als GitHub-Release (Server-Installer unsigniert, mit `SHA256SUMS-Server.txt`); braucht Secret `CLIENT_SIGNATUR_SCHLUESSEL` und den committeten `desktop/update-schluessel.pub` (Einrichtung: `desktop/README.md`)
- **CI lokal vorab laufen lassen:** (Pre-Push-Hook = `node scripts/ci-lokal.mjs --schlank`: Unit-Tests + nur die zu den noch nicht gepushten Änderungen passenden E2E-Specs, keine Sync- und keine Cluster-Suite (beide laufen im PR in der CI); vollständig: `npm run ci:lokal` (`scripts/ci-lokal.mjs`) wählt wie der `plan`-Job anhand der geänderten Dateien gegen `origin/main` (plus uncommittete) die passenden Gruppen (`unit`, `shellcheck` falls installiert, `test:e2e` + `:sync`, `:cluster`, `smoke-server-eingebettet`) und führt sie aus; Optionen `--alles`, `--nur-anzeigen`, `--base <ref>`, `--weiter`, `--paket` (Server-Paket bauen + Rauchtest), `--docker` (cluster-installation). Die Pfadfilter liest das Script aus `.github/ci-filter.yml`, wie der `plan`-Job. Prüft nur das eigene Betriebssystem, macOS bleibt der CI vorbehalten. Pre-Push-Hook `.githooks/pre-push` ruft das Script vor jedem Push auf; einmalig pro Klon aktivieren mit `git config core.hooksPath .githooks`, überspringen mit `git push --no-verify` oder `HAJIME_CI_UEBERSPRINGEN=1`
- **Server-Paket ("Hajime Pro Server", `desktop/server/`):** Notebook (Windows/macOS/Linux) als Hallen-Server und Frontend in einem — eigenes Paket neben dem Client (App-ID `de.hajime-pro.server`, `desktop/electron-builder.server.yml`): `npm run desktop:server:start` (lokal starten), `npm run desktop:server:build` (Installer nach `dist-server/`), `npm run test:electron:server` (Rauchtest, nicht als root). Der Hauptprozess startet `src/app.js` im Modus `server` mit eingebettetem PostgreSQL (alle Daten im Profilordner: `pg/`, `dokumente/`, `client-downloads/`), zeigt das Frontend über `localhost` (läuft auch ohne Netzwerk) und bleibt beim Schließen des Fensters im Tray; „Server beenden" stoppt Datenbank und Server. **Selbst-Update beim Start (Windows und Linux-AppImage, installierte App; macOS nicht):** vor Datenbank/Server (im Start-Fenster, mit Meldungen „Suche nach Updates …“ / „Hole Update … aus git …“ und Fortschrittsbalken) fragt `desktop/server/selbstUpdate.js` das neueste GitHub-Release ab (`CLIENT_RELEASE_REPO`, Token `CLIENT_RELEASE_TOKEN` oder `update.json` im Profilordner); nur eine NEUERE Version wird geladen, gegen die Ed25519-Signatur aus `server-version.json` geprüft (erzeugt in `release.yml` mit `signiere-client.mjs … server-version.json`), nach einem kurzen Hinweis im Fenster (3 Sekunden, kein Dialog) installiert (Windows: `/S`, UAC, währenddessen zeigt `desktop/server/installFenster.js` ein kleines Hajime-Fenster „Version … wird installiert“ mit Laufzeit und unbestimmtem Balken, das sich nach der Installation schließt; Linux: die laufende AppImage wird ersetzt) und die App startet neu; bei laufendem Server sucht er stündlich weiter, ein dann geladenes Update wird nicht mitten im Betrieb installiert, sondern beim nächsten Start (oder per Menü „Server“); ohne Internet/ohne Neueres/bei Fehlern startet der Server normal, höchstens 2 Versuche je Zielversion (`selbstupdate.json`), abschaltbar mit `HAJIME_SELBSTUPDATE=false`. Im Netzwerk erreichbar (mDNS `turnier.local`, Client-Installer über `/download`); Windows-Installer legt die Firewall-Regel für das private Netzwerk an (`desktop/build/server-installer.nsh`, UAC-Bestätigung). CI: `.github/workflows/server-paket.yml` (Build + Rauchtest der gebauten App auf Windows/Linux, macOS arm64 nur im Release (Eingabe `macos`); läuft im Release und auf Knopfdruck (Actions → Server-Paket → Run workflow), nicht mehr in der PR-CI).
- **Desktop-Client bauen/testen:** `npm run desktop:start` (Electron-Hülle lokal starten), `npm run desktop:build` (Distributionspakete nach `dist-desktop/`), `npm run desktop:icon` (App-Icon erzeugen, nicht Teil der CI — Icon ist committet), `npm run test:electron` (Playwright-Rauchtest gegen die gebaute/gestartete App). Update-Signatur: `npm run client:schluessel` (einmalig, Schlüsselpaar), `npm run client:signieren` (Release-Dateien signieren + `version.json`, läuft in der Pipeline), `npm run client:holen` (Client-Release vom Hallen-Server laden und Signatur prüfen). Details: `desktop/README.md`
- **Android-App (Client-Gerät auf Handy/Tablet, `mobil/`):** `npm run android:apk` (Web-Verzeichnis + Capacitor-Sync + Gradle → `dist-android/Hajime-Pro-<version>.apk`; JDK 21 + Android-SDK nötig; mit `HAJIME_KEYSTORE`/`HAJIME_KEYSTORE_PASSWORD`/`HAJIME_KEY_ALIAS`/`HAJIME_KEY_PASSWORD` Release-Signatur, sonst Debug-APK), `npm run android:www` (nur `mobil/www` neu bauen), `npm run test:e2e:mobil` (`playwright.mobil.config.js`, `tests/e2e-mobil/`: App-Web-Schicht unter eigener Herkunft `localhost:3401` gegen echten Hallen-Server `3400`; `HAJIME_PW_CHANNEL=msedge|chrome` nutzt einen vorhandenen Browser). Aufbau, Kopplung, Grenzen (kein iOS, keine mDNS-Suche, manuelle Updates): `mobil/README.md`
- **Client-Dateien am Server (automatisch):** `src/sync/clientDateien.js` stellt beim Serverstart unter `<CLIENT_DOWNLOADS_VERZEICHNIS>/<version>/` Windows/macOS/Linux/Android samt `version.json` bereit — erst aus den im Server-Paket mitgelieferten, in der Release-Pipeline signierten Dateien (`CLIENT_DATEIEN_MITGELIEFERT`, vom Electron-Hauptprozess gesetzt, `extraResources` `client-dateien/` in `desktop/electron-builder.server.yml`), sonst aus dem GitHub-Release zur Serverversion (`CLIENT_RELEASE_REPO`, bei privatem Repository `CLIENT_RELEASE_TOKEN`; `CLIENT_AUTO_HOLEN=false` schaltet ab, in `NODE_ENV=test` standardmäßig aus), mit Wiederholung alle 15 Min. nach Fehlern; jede Datei wird gegen die Ed25519-Signatur geprüft, `version.json` kommt zuletzt, `/api/client/version` liefert bis dahin 404 samt `status` (Download-Seite zeigt den Fortschritt). Release-Pipeline (`release.yml`): `build` + `android` → `signieren` (alle vier Plattformen Pflicht) → `server-paket` (mit `client-dateien`) → `veroeffentlichen`; Android-Secrets `ANDROID_KEYSTORE_BASE64`/`ANDROID_KEYSTORE_PASSWORD`/`ANDROID_KEY_ALIAS`/`ANDROID_KEY_PASSWORD` einmalig mit `npm run android:schluessel` erzeugen. `npm run client:holen` bleibt als manueller Abruf
- **Selbst-Update des Linux-Dienstes (Hallen-Server ohne Desktop, `install.sh`/systemd):** `src/utils/dienstUpdate.js`, aufgerufen früh in `src/app.js`. Aktiv nur im Modus `server` unter systemd (`INVOCATION_ID`), nicht im Cluster (`CLUSTER_KNOTEN`: zwei Server dürfen nicht gleichzeitig neu starten, dort Update per Knopf auf `cluster.html` bzw. von Hand mit `update.sh`), nicht mit `HAJIME_SELBSTUPDATE=false`. Beim Start fragt es das neueste GitHub-Release ab (`CLIENT_RELEASE_REPO`, Token `CLIENT_RELEASE_TOKEN`), lädt bei einer NEUEREN Version das Dienst-Paket `Hajime-Pro-Dienst-<version>.tar.gz` (in `release.yml` gepackt, Plattform `linux-dienst` in `server-version.json`), prüft die Ed25519-Signatur, entpackt es nach `<Installationsordner>/.update/neu-<version>/`, führt dort `npm ci --omit=dev` und `knex migrate:latest` aus und tauscht dann Code und `node_modules` aus (`.env` und `data/` bleiben; die vorherige Version liegt unter `.update/alt-<version>/` zum Zurückrollen). Danach beendet sich der Prozess und systemd startet die neue Version (`Restart=always`). Ohne Internet, ohne Neueres oder bei Fehlern (Prüfung, npm, Migration) läuft die vorhandene Version weiter, höchstens 2 Versuche je Zielversion (`data/selbstupdate.json`). Der Start wartet auf Prüfung und Download.
- **Anzeige des Update-Ablaufs (alle Installationen):** Texte und Balken kommen aus `src/shared/updateAnzeige.js`. Ohne Fenster (Linux-Dienst) schreibt `dienstUpdate.js` in Terminal bzw. `journalctl -u hajime-pro -f`: `Suche nach Updates …`, `Hole Update <version> aus git (GitHub-Release) …` mit Textbalken (im Terminal eine sich überschreibende Zeile, im Journal in 10-%-Schritten), beim Installieren `(1/4) Entpacke … (2/4) Installiere Abhängigkeiten … (3/4) Migriere die Datenbank … (4/4) Tausche die Programmdateien aus …` und vor dem Neustart `Update installiert – Neustart in 3 Sekunden …`. Desktop-Client und Server-Paket zeigen dieselben Meldungen im Start-Fenster mit Fortschrittsbalken (Client: `Hole Update … vom Server …`), die Android-App in der Statusleiste. Der Hinweis vor dem Neustart ist nur eine Meldung, kein Dialog.
- **Clients folgen dem laufenden Server:** Der Desktop-Client (`desktop/updater.js`) und die Android-App fragen beim Start `/api/client/version` des Hallen-Servers und laden die Datei der eigenen Plattform von dort (`/downloads/<version>/<datei>`). Der Server holt die Client-Dateien zur eigenen Version beim Start von GitHub (`src/sync/clientDateien.js`); aktualisiert sich der Server, folgen die Clients beim nächsten Start. **Android:** nur bei einer NEUEREN Server-Version (kein Downgrade) lädt `AppUpdatePlugin` (`mobil/android/…/AppUpdatePlugin.java`) die APK, prüft die SHA-256-Summe aus `version.json` und öffnet den Android-Installationsdialog; der Nutzer bestätigt, einmalig muss „Installation unbekannter Apps“ erlaubt werden (die App öffnet die Einstellung). Pro App-Sitzung ein Versuch je Version; Entscheidungslogik `src/shared/appUpdate.js`. Die APK wird nur im Release gebaut (`release.yml`); lokal prüfbar mit `npm run android:apk`.

- **Öffentliches Release-Repository (Code bleibt privat):** `release.yml` legt das Release im öffentlichen Repository `oensel/Hajime-Pro-Releases` an (Secret `RELEASES_REPO_TOKEN`: fine-grained Token nur für dieses Repository, Contents: write; das Repository braucht einen ersten Commit, z. B. die README aus `docs/releases-repo-README.md`). Alle Abrufe (`CLIENT_RELEASE_REPO`, Standard `oensel/Hajime-Pro-Releases`) brauchen dadurch keinen Token. Linux-Installation/-Update ohne Git: `deploy/linux/holen.sh` (als Asset `hajime-holen.sh` im Release) lädt das Dienst-Paket, prüft die Summe und entpackt es nach `/opt/hajime-quelle`; `update.sh`/`hajime-update.sh` nutzen es. Ein manuell gestarteter Release setzt den Quell-Tag im privaten Repository selbst.
- **Cloud-Update (Windows und Linux, Spec in Code-Kommentaren):** der Cloud-Server holt Updates aus dem öffentlichen Release-Repository, wie der Linux-Dienst (`src/utils/dienstUpdate.js`: Signatur, Prüfsumme, `npm ci`, Migration, Austausch). **Befehl:** `node scripts/cloud-update.mjs [--ziel <Ordner>] [--env-datei <Datei>] [--nur-pruefen] [--ohne-neustart]` (Standard: der eigene Ordner; ein neuer Zielordner wird erstmalig eingerichtet, `scripts/` stammt dann aus dem aufrufenden Ordner, falls das Paket sie noch nicht enthält; Konfiguration und Daten bleiben unberührt). Neustart: `CLOUD_NEUSTART_BEFEHL` (z. B. `systemctl restart hajime-cloud`), sonst die Datei `data/neustart.anfordern`, die `node scripts/cloud-lokal.mjs start` (Überwacher, setzt `HAJIME_UEBERWACHT=1`) beobachtet. **Oberfläche:** Bereich „Server-Update“ auf `admin-nutzer.html` (nur Super-Admin, `GET /api/cloud-update/status`, `POST /api/cloud-update/start`, `src/utils/cloudUpdate.js`, `public/js/adminUpdate.js`): der Server beendet sich nach der Installation mit Exit-Code 75, den Wiederanlauf übernehmen systemd (`Restart=always`) bzw. `cloud-lokal.mjs`; ohne Überwacher und im Docker-Container (dort wird das Image getauscht) ist der Knopf gesperrt, `HAJIME_CLOUD_UPDATE=false` schaltet ihn ab. Mit `DB_URL_MIGRATION` migriert das Update über die Migrations-Verbindung (`online-migration`). **Windows:** eine laufende PostgreSQL aus `node_modules` sperrt den Austausch; das Update bereitet nur vor (`.update/austausch.json`), `cloud-lokal.mjs` stoppt beim Neustart die PostgreSQL, tauscht aus (`fuehreVorgemerktenAustauschAus`) und startet alles neu; Umbenennen wiederholt bei EPERM (Virenscanner). Das Dienst-Paket enthält dafür `scripts/cloud-lokal.mjs`, `cloud-update.mjs` und `lokale-pg.mjs` (ab 1.0.25). Tests: `tests/unit/cloudUpdate.test.js`
