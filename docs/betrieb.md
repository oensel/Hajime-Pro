# Betrieb, Installation und Release

Übersicht, welche Geräte Server oder Client sind: [`betriebsarten.md`](betriebsarten.md). Aus `CLAUDE.md` ausgelagert (Stand v1.0.10). Hinweise zu Betriebsmodi, DB und Tests stehen weiter in `CLAUDE.md`.

- **Server-Cluster (zwei Hallen-Server, Master/Secondary):** zusätzlich zu `BETRIEBSMODUS=server` (PostgreSQL ist dort Standard): `SYNC_SECRET` (Pflicht im Cluster, auf beiden Servern gleich — ohne verweigert der Server den Start, `clusterSecretFehler` in `src/cluster/konfig.js`), `CLUSTER_KNOTEN` (`server1`|`server2`), `CLUSTER_PARTNER_URL` (feste Adresse des anderen Servers), optional `CLUSTER_VIP` (Anzeige), `CLUSTER_ZEUGE` (IP → Ping, URL → GET; leer = Default-Gateway), `CLUSTER_RUECKSTUFEN_BEFEHL` (Standard `sudo -n /usr/local/bin/hajime-rueckstufen.sh`). Ohne `CLUSTER_KNOTEN` ist der Server wie bisher immer Master. Betrieb (PostgreSQL-Replikation, keepalived, Skripte, Abnahme-Checkliste): `deploy/linux/README.md`
- **Neuen Hallen-Server aufsetzen (ein Befehl):** `sudo bash deploy/linux/install.sh` auf frischem Debian/Ubuntu (Node.js, PostgreSQL, `.env` mit Zufallsgeheimnissen, Migrationen, systemd-Autostart, ufw); wiederholbar als Update, kein Cluster (siehe `deploy/linux/README.md`)
- **Zwei-Server-Cluster einrichten (geführt):** `sudo bash deploy/linux/install-cluster.sh --knoten server1|server2 --eigene-ip … --partner-ip … --vip …` auf beiden Servern (server1 zuerst, Geheimnis-Datei per scp zu server2); installiert Node.js, PostgreSQL-Replikation, keepalived, `.env`, systemd, ufw; `hajime-cluster-status` zeigt den Zustand; `--nur-konfig <Verzeichnis>` erzeugt nur die Konfigurationsdateien (Unit-Test `tests/unit/install-cluster.test.js`, CI-Job `cluster-installation` baut den Cluster in zwei Docker-systemd-Containern auf und prüft Failover)
- **Cloud-Modus (`BETRIEBSMODUS=cloud`) und Docker:** PostgreSQL-Verbindung über `DB_URL` (Alias `DATABASE_URL`, z.B. Supabase-Pooler) oder die Einzelvariablen `DB_HOST`/…; die URL gewinnt (`src/config/dbVerbindung.cjs`, Unit-Tests `tests/unit/dbVerbindung.test.js`). `DB_SSL=true|no-verify|false` (Standard bei URL `no-verify`, sonst `false`; `sslmode` in der URL wird entfernt), `DB_POOL_MAX`, optional `DB_URL_MIGRATION` (Direct-/Session-Verbindung, Umgebung `online-migration` in `knexfile.cjs`, da der Transaction-Pooler keine Migrationen verträgt) und `DB_AUTO_MIGRATE=true` (migriert beim Start über `DB_URL_MIGRATION`, Standard aus). `Dockerfile` + `docker-compose.yml` (Profile `cloud` gegen Supabase, `lokal` mit eigenem Postgres), Konfiguration aus `.env.cloud.example` → `.env.cloud`; Healthcheck auf `/api/config`; Workflow `.github/workflows/docker-cloud.yml` baut das Image nur manuell (`workflow_dispatch`), nicht Teil von `ci.yml`
- **CI/Release-Pipeline (Stages dev → test → qa → prod):** `.github/workflows/ci.yml` (PR, Push auf `main`, nächtlich 02:17 UTC, manuell, auch als `workflow_call`) — `dev` (Ubuntu, billig: `plan` mit Pfadfiltern via `dorny/paths-filter`, `unit`, `shellcheck`), `test` (`test:e2e` + `test:e2e:sync`, nur bei Änderungen an `src/`, `public/`, `migrations/`, `tests/` …), `qa` (teuer: `server-selbststart` auf Ubuntu/Windows nur bei Änderungen am eingebetteten PostgreSQL/Betriebsmodus/Migrationen, `cluster-installation` (Docker) + `e2e-cluster` nur bei `src/cluster|sync|shared`, `deploy/linux`, Cluster-Tests, `server-paket` (Aufruf von `server-paket.yml`, nur bei Paket-Pfaden, nicht bei Tag/Nachtlauf, kein eigener PR-Trigger mehr)); jede Stage braucht die vorherige grün (`needs`), `concurrency` bricht veraltete PR-Läufe ab. Voller Umfang ohne Filter bei Tag, Nachtlauf und manuellem Start (`plan` setzt dann alle Flags). `test:e2e:vollablauf` läuft bewusst nicht mit (schreibt in die echte Cloud-DB). `.github/workflows/release.yml` (Tag `v*` oder manuell: Actions → Release → Run workflow, Branch `main`, Version ohne `v`; beim manuellen Start legt `gh release create --target <Commit>` den Tag selbst an, bricht ab, wenn der Tag schon existiert oder der Branch nicht `main` ist; `RELEASE_TAG` ersetzt `GITHUB_REF_NAME`; `ci.yml` bekommt `release: true`, damit Server-Paket und APK nicht doppelt gebaut werden; Stage `prod`) ruft `ci.yml` auf, prüft Tag == `package.json`-Version, baut den Desktop-Client für Windows/macOS/Linux (+ Electron-Rauchtest je Plattform) und parallel das Server-Paket (`server-paket.yml`), signiert die Client-Dateien und veröffentlicht beides als GitHub-Release (Server-Installer unsigniert, mit `SHA256SUMS-Server.txt`); braucht Secret `CLIENT_SIGNATUR_SCHLUESSEL` und den committeten `desktop/update-schluessel.pub` (Einrichtung: `desktop/README.md`)
- **CI lokal vorab laufen lassen:** (Pre-Push-Hook = `node scripts/ci-lokal.mjs --schlank`: Unit-Tests + nur die zu den noch nicht gepushten Änderungen passenden E2E-Specs, Sync-Suite nur bei Änderungen an `src/sync`/`src/shared`/`datenzugriff.js`, keine Cluster-Suite; vollständig: `npm run ci:lokal`) `npm run ci:lokal` (`scripts/ci-lokal.mjs`) wählt wie der `plan`-Job anhand der geänderten Dateien gegen `origin/main` (plus uncommittete) die passenden Gruppen (`unit`, `shellcheck` falls installiert, `test:e2e` + `:sync`, `:cluster`, `smoke-server-eingebettet`) und führt sie aus; Optionen `--alles`, `--nur-anzeigen`, `--base <ref>`, `--weiter`, `--paket` (Server-Paket bauen + Rauchtest), `--docker` (cluster-installation). Die Pfadfilter im Script müssen mit denen in `ci.yml` übereinstimmen. Prüft nur das eigene Betriebssystem, macOS bleibt der CI vorbehalten. Pre-Push-Hook `.githooks/pre-push` ruft das Script vor jedem Push auf; einmalig pro Klon aktivieren mit `git config core.hooksPath .githooks`, überspringen mit `git push --no-verify` oder `HAJIME_CI_UEBERSPRINGEN=1`
- **Server-Paket ("Hajime Pro Server", `desktop/server/`):** Notebook (Windows/macOS/Linux) als Hallen-Server und Frontend in einem — eigenes Paket neben dem Client (App-ID `de.hajime-pro.server`, `desktop/electron-builder.server.yml`): `npm run desktop:server:start` (lokal starten), `npm run desktop:server:build` (Installer nach `dist-server/`), `npm run test:electron:server` (Rauchtest, nicht als root). Der Hauptprozess startet `src/app.js` im Modus `server` mit eingebettetem PostgreSQL (alle Daten im Profilordner: `pg/`, `dokumente/`, `client-downloads/`), zeigt das Frontend über `localhost` (läuft auch ohne Netzwerk) und bleibt beim Schließen des Fensters im Tray; „Server beenden" stoppt Datenbank und Server. **Selbst-Update beim Start (Windows und Linux-AppImage, installierte App; macOS nicht):** vor Datenbank/Server (im Start-Fenster, mit Meldungen „Suche nach Updates …“ / „Hole Update … aus git …“ und Fortschrittsbalken) fragt `desktop/server/selbstUpdate.js` das neueste GitHub-Release ab (`CLIENT_RELEASE_REPO`, Token `CLIENT_RELEASE_TOKEN` oder `update.json` im Profilordner); nur eine NEUERE Version wird geladen, gegen die Ed25519-Signatur aus `server-version.json` geprüft (erzeugt in `release.yml` mit `signiere-client.mjs … server-version.json`), nach einem kurzen Hinweis im Fenster (3 Sekunden, kein Dialog) installiert (Windows: `/S`, UAC, währenddessen zeigt `desktop/server/installFenster.js` ein kleines Hajime-Fenster „Version … wird installiert“ mit Laufzeit und unbestimmtem Balken, das sich nach der Installation schließt; Linux: die laufende AppImage wird ersetzt) und die App startet neu; bei laufendem Server sucht er stündlich weiter, ein dann geladenes Update wird nicht mitten im Betrieb installiert, sondern beim nächsten Start (oder per Menü „Server“); ohne Internet/ohne Neueres/bei Fehlern startet der Server normal, höchstens 2 Versuche je Zielversion (`selbstupdate.json`), abschaltbar mit `HAJIME_SELBSTUPDATE=false`. Im Netzwerk erreichbar (mDNS `turnier.local`, Client-Installer über `/download`); Windows-Installer legt die Firewall-Regel für das private Netzwerk an (`desktop/build/server-installer.nsh`, UAC-Bestätigung). CI: `.github/workflows/server-paket.yml` (Build + Rauchtest der gebauten App auf Windows/Linux, macOS arm64 nur im Release (Eingabe `macos`); bei PRs, die das Paket berühren, als `qa`-Job in `ci.yml` nach dem E2E-Kern, und im Release).
- **Desktop-Client bauen/testen:** `npm run desktop:start` (Electron-Hülle lokal starten), `npm run desktop:build` (Distributionspakete nach `dist-desktop/`), `npm run desktop:icon` (App-Icon erzeugen, nicht Teil der CI — Icon ist committet), `npm run test:electron` (Playwright-Rauchtest gegen die gebaute/gestartete App). Update-Signatur: `npm run client:schluessel` (einmalig, Schlüsselpaar), `npm run client:signieren` (Release-Dateien signieren + `version.json`, läuft in der Pipeline), `npm run client:holen` (Client-Release vom Hallen-Server laden und Signatur prüfen). Details: `desktop/README.md`
- **Android-App (Client-Gerät auf Handy/Tablet, `mobil/`):** `npm run android:apk` (Web-Verzeichnis + Capacitor-Sync + Gradle → `dist-android/Hajime-Pro-<version>.apk`; JDK 21 + Android-SDK nötig; mit `HAJIME_KEYSTORE`/`HAJIME_KEYSTORE_PASSWORD`/`HAJIME_KEY_ALIAS`/`HAJIME_KEY_PASSWORD` Release-Signatur, sonst Debug-APK), `npm run android:www` (nur `mobil/www` neu bauen), `npm run test:e2e:mobil` (`playwright.mobil.config.js`, `tests/e2e-mobil/`: App-Web-Schicht unter eigener Herkunft `localhost:3401` gegen echten Hallen-Server `3400`; `HAJIME_PW_CHANNEL=msedge|chrome` nutzt einen vorhandenen Browser). Aufbau, Kopplung, Grenzen (kein iOS, keine mDNS-Suche, manuelle Updates): `mobil/README.md`
- **Client-Dateien am Server (automatisch):** `src/sync/clientDateien.js` stellt beim Serverstart unter `<CLIENT_DOWNLOADS_VERZEICHNIS>/<version>/` Windows/macOS/Linux/Android samt `version.json` bereit — erst aus den im Server-Paket mitgelieferten, in der Release-Pipeline signierten Dateien (`CLIENT_DATEIEN_MITGELIEFERT`, vom Electron-Hauptprozess gesetzt, `extraResources` `client-dateien/` in `desktop/electron-builder.server.yml`), sonst aus dem GitHub-Release zur Serverversion (`CLIENT_RELEASE_REPO`, bei privatem Repository `CLIENT_RELEASE_TOKEN`; `CLIENT_AUTO_HOLEN=false` schaltet ab, in `NODE_ENV=test` standardmäßig aus), mit Wiederholung alle 15 Min. nach Fehlern; jede Datei wird gegen die Ed25519-Signatur geprüft, `version.json` kommt zuletzt, `/api/client/version` liefert bis dahin 404 samt `status` (Download-Seite zeigt den Fortschritt). Release-Pipeline (`release.yml`): `build` + `android` → `signieren` (alle vier Plattformen Pflicht) → `server-paket` (mit `client-dateien`) → `veroeffentlichen`; Android-Secrets `ANDROID_KEYSTORE_BASE64`/`ANDROID_KEYSTORE_PASSWORD`/`ANDROID_KEY_ALIAS`/`ANDROID_KEY_PASSWORD` einmalig mit `npm run android:schluessel` erzeugen. `npm run client:holen` bleibt als manueller Abruf
- **Selbst-Update des Linux-Dienstes (Hallen-Server ohne Desktop, `install.sh`/systemd):** `src/utils/dienstUpdate.js`, aufgerufen früh in `src/app.js`. Aktiv nur im Modus `server` unter systemd (`INVOCATION_ID`), nicht im Cluster (`CLUSTER_KNOTEN`: zwei Server dürfen nicht gleichzeitig neu starten, dort Update von Hand), nicht mit `HAJIME_SELBSTUPDATE=false`. Beim Start fragt es das neueste GitHub-Release ab (`CLIENT_RELEASE_REPO`, Token `CLIENT_RELEASE_TOKEN`), lädt bei einer NEUEREN Version das Dienst-Paket `Hajime-Pro-Dienst-<version>.tar.gz` (in `release.yml` gepackt, Plattform `linux-dienst` in `server-version.json`), prüft die Ed25519-Signatur, entpackt es nach `<Installationsordner>/.update/neu-<version>/`, führt dort `npm ci --omit=dev` und `knex migrate:latest` aus und tauscht dann Code und `node_modules` aus (`.env` und `data/` bleiben; die vorherige Version liegt unter `.update/alt-<version>/` zum Zurückrollen). Danach beendet sich der Prozess und systemd startet die neue Version (`Restart=always`). Ohne Internet, ohne Neueres oder bei Fehlern (Prüfung, npm, Migration) läuft die vorhandene Version weiter, höchstens 2 Versuche je Zielversion (`data/selbstupdate.json`). Der Start wartet auf Prüfung und Download.
- **Anzeige des Update-Ablaufs (alle Installationen):** Texte und Balken kommen aus `src/shared/updateAnzeige.js`. Ohne Fenster (Linux-Dienst) schreibt `dienstUpdate.js` in Terminal bzw. `journalctl -u hajime-pro -f`: `Suche nach Updates …`, `Hole Update <version> aus git (GitHub-Release) …` mit Textbalken (im Terminal eine sich überschreibende Zeile, im Journal in 10-%-Schritten), beim Installieren `(1/4) Entpacke … (2/4) Installiere Abhängigkeiten … (3/4) Migriere die Datenbank … (4/4) Tausche die Programmdateien aus …` und vor dem Neustart `Update installiert – Neustart in 3 Sekunden …`. Desktop-Client und Server-Paket zeigen dieselben Meldungen im Start-Fenster mit Fortschrittsbalken (Client: `Hole Update … vom Server …`), die Android-App in der Statusleiste. Der Hinweis vor dem Neustart ist nur eine Meldung, kein Dialog.
- **Clients folgen dem laufenden Server:** Der Desktop-Client (`desktop/updater.js`) und die Android-App fragen beim Start `/api/client/version` des Hallen-Servers und laden die Datei der eigenen Plattform von dort (`/downloads/<version>/<datei>`). Der Server holt die Client-Dateien zur eigenen Version beim Start von GitHub (`src/sync/clientDateien.js`); aktualisiert sich der Server, folgen die Clients beim nächsten Start. **Android:** nur bei einer NEUEREN Server-Version (kein Downgrade) lädt `AppUpdatePlugin` (`mobil/android/…/AppUpdatePlugin.java`) die APK, prüft die SHA-256-Summe aus `version.json` und öffnet den Android-Installationsdialog; der Nutzer bestätigt, einmalig muss „Installation unbekannter Apps“ erlaubt werden (die App öffnet die Einstellung). Pro App-Sitzung ein Versuch je Version; Entscheidungslogik `src/shared/appUpdate.js`. CI baut die Debug-APK bei Änderungen an `mobil/` (Job `qa / android-apk`), damit Fehler im nativen Teil nicht erst im Release auffallen.
