# Betrieb, Modi, Cloud-Update, Downloads

Ausgelagert aus der CLAUDE.md; nur lesen, wenn das Thema die Aufgabe betrifft.

- **Betriebsmodi (`BETRIEBSMODUS`, ausgewertet einmal in `src/config/betriebsmodus.cjs`):** `cloud` (Internet-Server, PostgreSQL/Supabase, Vereinsrechte mit Login), `server` (Hallen-Server: PostgreSQL + Dokument-DB lokal, Einzelbenutzer ohne Login; auf einem Notebook unter Windows/macOS/Linux oder auf Linux-Servern, dort optional im Cluster) und `client` (Gerät an Matte/Waage, nur lokale Dokument-DB, Installation über den Server). Ein Server bietet seine Dienste immer gleich an (alle Schnittstellen, mDNS `turnier.local`, Port 80): ob der Browser auf demselben Rechner läuft oder ein Client im LAN zugreift, macht keinen Unterschied, und ohne Netzwerk läuft er ebenfalls (nur `LISTEN_HOST=127.0.0.1` beschränkt ihn auf localhost). Ergänzend im Modus `server`: `CLUSTER_KNOTEN` (Cluster braucht einen eigenen PostgreSQL-Server) und `DB_HOST`/`DB_URL`: **ohne `DB_HOST`/`DB_URL` startet der Server sein eigenes, eingebettetes PostgreSQL** (`src/utils/eingebettetesPostgres.js`, Binaries aus `embedded-postgres`, Datenverzeichnis `PG_DATENVERZEICHNIS`, Standard `./data/pg`, Port `DB_PORT`, Standard 5433, nur `127.0.0.1`, Log neben dem Datenverzeichnis; Schema wird bei jedem Start migriert; läuft bereits eine Instanz, wird sie übernommen; nicht als root startbar), mit `DB_HOST` nutzt er einen vorhandenen Server. Das eingebettete PostgreSQL gilt nur bei ausdrücklich gesetztem `BETRIEBSMODUS=server`; Rauchtest: `node scripts/smoke-server-eingebettet.mjs` (CI-Job `server-selbststart` auf Ubuntu/Windows, macOS vorerst nicht in der CI). Ungültige Kombinationen verhindern den Start mit Meldung. **Ohne `BETRIEBSMODUS`** gilt das bisherige Verhalten aus den Altvariablen: `SYNC_ROLLE=client` → `client`, `IS_OFFLINE=true` → `server` (PostgreSQL über `DB_HOST`/`DB_URL`, ohne diese Angabe Startabbruch mit Hinweis auf `BETRIEBSMODUS=server`; kein eingebettetes PostgreSQL; die Sync-Rolle kommt dort allein aus `SYNC_ROLLE`, also auch ein Server ohne Sync möglich — so laufen `test:e2e` und der Offline-Teil von `test:e2e:vollablauf`), sonst `cloud`. Im Code fragt man `betriebsmodus.liesBetriebsmodus()` bzw. `istEinzelbenutzerBetrieb()`, nie direkt `process.env.IS_OFFLINE`
- **Helferverwaltung-Variablen:** `HELFER_APP_AKTIV=true` hängt `/api/helfer` (inkl. `/api/helfer/orga`) und `/api/einladung` auch außerhalb der Cloud ein (Tests/Entwicklung); der Orga-Erinnerungsjob startet nur in der Cloud bzw. mit `HELFER_APP_AKTIV`, nur mit gesetztem `SMTP_HOST` und nie bei `NODE_ENV=test`, `PUBLIC_BASE_URL` (Pflicht in der Cloud) bestimmt die Links in Registrierungs-/Freischaltungs-Mails; Mailversand braucht SMTP (siehe `docs/betrieb.md`); `AUTH_RATENLIMIT_AKTIV` (Standard: an in der Cloud, sonst aus) schaltet die Ratenbegrenzung von Registrierung/Login (`src/middleware/authRatenbegrenzung.js`)
- **Sync-Modus (Hallen-Server):** `BETRIEBSMODUS=server` (bzw. altes `SYNC_ROLLE=server`) (+ optional `SYNC_DATENVERZEICHNIS`, Standard `./data/dokumente`, und `SYNC_SECRET`) aktiviert die eingebettete Dokument-DB unter `/db`; genau ein Turnier pro Server, Anlegen/Import eines Turniers löscht das bisherige
- **Client-Gerät (Notebook/Tablet an Matte/Waage):** `BETRIEBSMODUS=client` (bzw. altes `SYNC_ROLLE=client`), `SYNC_SERVER_URL=http://<hallen-server>:3000`, `SYNC_SECRET` (wie am Server), optional `SYNC_DATENVERZEICHNIS`; `npm start`, Browser auf `http://localhost:3000` (Startseite `client.html`). Keine relationale DB, keine `DB_*`-Variablen nötig. Unter Windows das Datenverzeichnis möglichst vom Virenscanner ausnehmen (LevelDB-Dateien werden sonst gelegentlich beim Anlegen blockiert; `oeffneMitWiederholung` fängt das ab)
- **Server-Cluster, Hallen-Server-/Cluster-Installation, Cloud/Docker, CI/Release, Server-Paket, Desktop-Client, Android-App, Client-Dateien:** Geräte-/Rollen-Matrix in [`docs/betriebsarten.md`](docs/betriebsarten.md), Betriebs- und Release-Details in [`docs/betrieb.md`](docs/betrieb.md); Cluster-Betrieb zusätzlich in `deploy/linux/README.md`, Desktop in `desktop/README.md`. Wichtig: `npm run ci:lokal` lässt die CI vorab lokal laufen (der Pre-Push-Hook nutzt die schlanke Variante `--schlank`: Unit-Tests + nur die zu den noch nicht gepushten Änderungen passenden E2E-Specs, volle Suite mit `npm run ci:lokal` bzw. in der CI; Umgehen nur mit `HAJIME_CI_UEBERSPRINGEN=1`); `test:e2e:vollablauf` läuft bewusst nicht in der CI.
- **Sync-Suite:** `npm run test:e2e:sync` (`scripts/test-e2e-sync.mjs`) startet die Shards aus `tests/e2e-sync/shards.js` (`server`, `client`, `verbindung`) GLEICHZEITIG als eigene Playwright-Läufe; jeder Shard hat ein eigenes Knotenpaar: Hallen-Server (`BETRIEBSMODUS=server`, Port 3200+2n, eigenes eingebettetes PostgreSQL Port 5602+n unter `data/test-sync-pg[-n]`, startet der Server selbst, `data/test-sync-dokumente[-n]/`) und Client-Gerät (`BETRIEBSMODUS=client`, Port 3201+2n, `data/test-sync-client[-n]/`), `n` kommt aus `HAJIME_SYNC_SHARD` (`tests/e2e-sync/test-env.js`; ohne die Variable läuft alles in einem Lauf mit den Werten von Shard 0 ohne Suffix, z.B. `npx playwright test -c playwright.sync.config.js tests/e2e-sync/<datei>`). Jede Spec-Datei muss in `shards.js` genau einmal stehen (die Config bricht sonst ab); nur ein Shard: `npm run test:e2e:sync -- --shard client`. Innerhalb eines Shards laufen die Specs seriell und bauen auf demselben Turnier-Zustand auf. Testdaten werden in `playwright.sync.config.js` VOR dem Serverstart gelöscht (der Client fragt beim Start sofort den Server). Test-Endpunkte (nur `NODE_ENV=test`): `POST /api/sync/test/leerlauf` (Server: Brücke+Abgleich fertig; Client: alles übertragen), `POST /api/sync/test/trennen|verbinden` (Client offline/online), `GET /api/sync/test/verworfen`. Helfer in `tests/e2e-sync/helpers.js` (`syncLeerlauf`, `clientTrennen`, …); direkte `/db`-Zugriffe senden per `extraHTTPHeaders` das `SYNC_SECRET`
- **Cluster-Suite:** `npm run test:e2e:cluster` (`playwright.cluster.config.js`, `tests/e2e-cluster/`) — läuft ohne Docker, auch unter Windows: der Leitstand (`tests/e2e-cluster/leitstand.js`, webServer der Suite, Steuer-API Port 3309) baut zwei lokale PostgreSQL-Instanzen (Binaries aus der devDependency `embedded-postgres`, Ports 5511/5512, Standby per Low-Level-Backup-API statt `pg_basebackup`), zwei Hallen-Server (3311/3312) und ein Client-Gerät (3313) auf und simuliert keepalived (Gesundheit, `nopreempt`), die VIP (HTTP-Proxy 3310, `baseURL` der Tests) und den Zeugen. Ausfälle per `POST /knoten/:k/stoppen|starten`, `POST /zeuge/:k/trennen|verbinden`; Daten unter `data/test-cluster/` (Server-Logs in `logs/`). Die Tests bauen seriell aufeinander auf
- Neue Server-Variablen für den Desktop-Client: `MDNS_AKTIV` (Default an, `false` deaktiviert die mDNS-Ankündigung), `MDNS_NAME` (Hostname der Ankündigung: der Server ist als `<MDNS_NAME>.local` erreichbar, Default `turnier`), `PORT80_WEITERLEITUNG` (Default an, leitet Port 80 zusätzlich weiter), `CLIENT_DOWNLOADS_VERZEICHNIS` (Ablage der zum Download angebotenen Client-Dateien, Default `./data/client-downloads`). Ohne `SYNC_SECRET` erzeugt der Hallen-Server es selbst und schreibt es nach `<SYNC_DATENVERZEICHNIS>/kopplung.json`; bestehende Client-Geräte mit eigener `.env` müssen dieses Geheimnis dann übernehmen
- **Cloud-Update (Befehl `node scripts/cloud-update.mjs`, eigener Menüpunkt „Server-Update“ mit der Seite `server-update.html` für Super-Admins):** `src/utils/cloudUpdate.js` + `routes/cloudUpdateRoutes.js` (`/api/cloud-update/status|start`, nur Cloud) nutzen `installiereDienstPaket` aus `src/utils/dienstUpdate.js` (Release-Paket aus `oensel/Hajime-Pro-Releases`); nach der Installation Exit-Code 75, Wiederanlauf durch systemd bzw. den Überwacher `scripts/cloud-lokal.mjs` (Windows: Austausch erst beim Neustart, `austausch: 'spaeter'`); Details in `docs/betrieb.md`
- **Downloads über die Cloud (Spec `docs/specs/2026-10-24-downloads-ueber-cloud-design.md`, Betrieb in `docs/betrieb.md`):** die Cloud spiegelt Releases aus dem privaten Repository (`RELEASE_QUELLE_REPO`/`_TOKEN`), bietet sie auf `downloads.html` (Rolle ab Benutzer, Mitgliedschaft freigegeben) per Einmal-Ticket an und liefert Hallen-Servern unter `/api/releases/v1` (GitHub-kompatibel) Updates; Geräteschlüssel (`download_schluessel`) entstehen aus dem Einlösecode im Installer-Dateinamen bzw. bei der Cloud-Anmeldung, Quellenwahl in `src/utils/releaseQuelle.js` (ohne Schlüssel weiter GitHub, Übergang). Tests: `downloads.test.js`, `releaseQuelle.test.js`
- **Turnier aus der Cloud holen (Hallen-Server, Spec `docs/specs/2026-10-15-turnier-aus-cloud-holen-design.md`):** `CLOUD_URL` (`.env`, ohne Wert gibt es die Funktion nicht) zeigt auf die Cloud; `turniere.html` blendet unter dem lokalen Turnier den Bereich „Turniere aus der Cloud“ ein, wenn `GET /api/cloud/status` die Cloud als erreichbar meldet. Anmeldung mit Cloud-Benutzer/-Passwort (`POST /api/cloud/turniere`, nichts wird gespeichert, das Token liegt nur im Arbeitsspeicher der Seite), Holen per `POST /api/cloud/turniere/:id/holen` → Export der Cloud → `importiereTurnierDaten` (derselbe Kern wie der Datei-Import, ersetzt das bisherige Turnier). Nur ab Anmeldeschluss (Export-Regel der Cloud). `src/services/cloudZugriff.js` (HTTP, Timeouts, nur `CLOUD_URL`), `src/routes/cloudRoutes.js` (nur Einzelbenutzerbetrieb, am Secondary aus). Ein 401 der Cloud geht als 422 an den Browser, weil `menu.js` bei 401 auf die Anmeldeseite umleitet. Tests: `tests/unit/cloudZugriff.test.js`, `tests/e2e/turnier-aus-cloud-holen.spec.js` (Fake-Cloud `tests/helpers/fake-cloud.mjs`, Port 3190)
